Preface

Red Hat Developer Hub Intelligent Assistant (formerly Developer Lightspeed for Developer Hub) is an AI-powered virtual assistant for Red Hat Developer Hub (RHDH). You can interact with the Intelligent Assistant to explore RHDH capabilities in detail.

Chapter 1. Chat assistance with Developer Hub Intelligent Assistant

Use Developer Hub Intelligent Assistant to find product information, discover features, and resolve technical questions using natural language prompts directly within the RHDH console.

To speed up repeat tasks, you can save prompts that you enter frequently and reuse them in any chat session without retyping them.

Chapter 2. Red Hat Developer Hub Intelligent Assistant architecture for your AI backend deployment

Review the Developer Hub Intelligent Assistant component architecture to plan your system layout and coordinate connections with your artificial intelligence (AI) backend deployment.

The architecture relies on the Lightspeed Core Service (LCORE) container, which operates as the primary intermediary layer to manage Developer Hub Intelligent Assistant functionality and console user interactions. After you enable the plugin, the interface appears as the Intelligent Assistant button on all platforms that host RHDH.

Developer Hub Intelligent Assistant connects only to LCORE. LCORE manages the configuration for the model inference, query validation, tool calling, and the vector store. You configure these capabilities through LCORE, and Developer Hub Intelligent Assistant consumes them through LCORE APIs.

Open GenAI Stack (OGX) is an internal implementation detail of LCORE and is not a customer-facing component. Do not configure OGX directly, call OGX APIs, or edit the generated /tmp/.generated/run.yaml file. Configure LCORE instead, so that your deployment stays stable across OGX changes.

2.1. AI reference and tool-calling capabilities through Lightspeed Core Service

Review the core components managed by the Lightspeed Core Service (LCORE) sidecar container to plan integrations with large language models (LLM) and tool runtime providers.

The LCORE container deploys as a sidecar to extend RHDH functionality, and it integrates and manages the following core components:

  • Large language model (LLM) inference providers

  • Model Context Protocol (MCP) or Retrieval Augmented Generation (RAG) tool runtime providers

    Important

    Verify that your model supports tool calling before you enable MCP features. Using an incompatible model results in error messages.

  • Safety providers
  • Vector database settings

LCORE also manages the following operational data:

  • User feedback collection
  • MCP server configuration
  • Chat history

All prompts and LLM responses pass through the LCORE sidecar.

Chapter 3. Retrieval augmented generation (RAG) embeddings for grounded AI responses

Use retrieval-augmented generation (RAG) embeddings to ground artificial intelligence (AI) responses in your internal documentation and provide verified citations during user interactions.

The RHDH documentation serves as the primary data source for RAG operations. To provide accurate citations to production documentation during inference, the system uses RAG embeddings stored within a vector database.

The system processes RAG data through the following sequence:

  • An initialization container copies the RAG data to a shared volume.
  • The Lightspeed Core Service (LCORE) sidecar container mounts the shared volume to access the data.
  • The sidecar layer uses the embeddings to attach precise documentation references to the chat responses.

Chapter 4. Configure Developer Hub Intelligent Assistant to initialize the AI assistant

Red Hat Developer Hub Intelligent Assistant is enabled by default on Red Hat Developer Hub (RHDH) instances. To provide developers with chat assistance, configure your deployment settings by using either the Operator or the Helm chart.

4.1. Configure the virtual assistant components

Configure Developer Hub Intelligent Assistant by updating your Backstage custom resource (CR) to map environment variables, manage configurations, and set access rights.

Prerequisites

  • The RHDH Operator is installed on your cluster.
  • You have cluster administrator privileges.

Procedure

  1. Create an opaque Kubernetes Secret containing your operational credentials and query validation keys before applying the Backstage CR. Refer to the following key definitions for required environment variables:

    Important

    The Secret supplies only provider credentials and endpoints. To enable an inference provider, define it as an entry under the inference.providers section of the lightspeed-stack.yaml file. Adding a credential key to the Secret does not enable a provider on its own.

    KeyDescription

    VLLM_URL

    Specifies the target API endpoint URL for vLLM. The URL must end in /v1, for example, https://<api_endpoint>/v1.

    VLLM_API_KEY

    Stores the authorization token for your vLLM platform.

    OPENAI_API_KEY

    Stores the authorization secret key for OpenAI.

    VERTEX_AI_PROJECT

    Specifies your Google Cloud project ID.

    VERTEX_AI_LOCATION

    Specifies your target Google Cloud region.

    GOOGLE_APPLICATION_CREDENTIALS

    Specifies the in-container file path of your mounted Google Cloud service account credentials JSON file.

    ENABLE_VALIDATION

    Enables the question-validity shield when set to question_validity. Leave the variable unset, or set it to disabled, to keep validation disabled. A nonempty value such as true does not enable the shield.

    VALIDATION_PROVIDER

    Specifies the type of the inference provider that runs the classification, for example, openai or vllm. A provider of this type must be enabled in inference.providers.

    VALIDATION_MODEL_NAME

    Specifies the model that classifies each prompt, for example, gpt-4o-mini.

    The following code shows an example configuration Secret for vLLM with validation: 

    apiVersion: v1
kind: Secret
metadata:
  name: intelligent-assistant-auth-secrets
type: Opaque
stringData:
  VLLM_URL: "https://<api_endpoint>/v1"
  VLLM_API_KEY: "<api_key>"
  ENABLE_VALIDATION: question_validity
  VALIDATION_PROVIDER: "vllm"
  VALIDATION_MODEL_NAME: "llama3.1"
    Note

    The VALIDATION_PROVIDER value is the inference provider type, such as vllm or openai. A provider of this type must be enabled in the inference.providers section of the lightspeed-stack.yaml file.

  2. Enable at least one inference provider by defining it under the inference.providers section of the lightspeed-stack.yaml file. Creating the Secret alone does not enable a provider. For the provider entry format and the Secret keys that each provider requires, see the inference provider configuration reference for Developer Hub Intelligent Assistant.

  3. Map your secret inside the extraEnvs section of the Backstage CR to complete container provisioning: 

    apiVersion: rhdh.redhat.com/v1alpha5
kind: Backstage
metadata:
  name: intelligent-assistant-rhdh
spec:
  application:
    extraEnvs:
      secrets:
        - name: intelligent-assistant-auth-secrets
          containers:
            - lightspeed-core

  4. Optional: To protect settings such as Model Context Protocol (MCP) server additions from being overwritten during reconciliation loops, define a custom ConfigMap mapping in the extraFiles section of the CR: 

        extraFiles:
      configMaps:
        - name: "my-custom-config"
          mountPath: /app-root
          key: lightspeed-stack.yaml
          containers:
            - lightspeed-core

  5. Configure access rights by updating the RBAC policy inside your Backstage CR:

    To grant non-administrator teams access to the virtual assistant, append permission lines to the rbac-policies.csv section, replacing <team> with your target team name: 

    p, role:default/<team>, intelligent-assistant.chat, use, allow 1
    <1>

    Grants full use of the Developer Hub Intelligent Assistant chat feature, including opening the chat window, sending messages, managing chat history, and saving and reusing chat prompts.

    For the complete list of AI feature permissions, including Notebooks, MCP tools, and skills, see AI feature permissions.

  6. Apply the updated custom resource manifest to your cluster: 

    $ oc apply -f <backstage_cr_file>.yaml

Verification

  1. Log in to your console instance.
  2. Verify that the Intelligent Assistant button appears on the home page.
  3. Select the Intelligent Assistant button and confirm that the chat window initializes successfully.

4.3. Inference provider configuration reference for Developer Hub Intelligent Assistant

To give Developer Hub Intelligent Assistant access to a model, define each inference provider as an entry under the top-level inference.providers section of the lightspeed-stack.yaml file.

The provider entry enables the provider. Adding an API key or an ENABLE_* variable to the Secret does not enable a provider on its own.

Keep the sentence_transformers provider when you add a large language model (LLM) provider. It supports the default embedding path that the shipped vector store uses.

Each LLM provider entry requires a unique id. The api_key_env field contains the name of an environment variable, not ${env…​} syntax and not the credential value. Lightspeed Core Service (LCORE) resolves the variable without exposing the key in the configuration file.

OpenAI

Set type to openai, and add OPENAI_API_KEY to the Secret. Use extra.allowed_models to limit model registration. If you omit it, the provider registers every model that is visible to the account. 

inference:
  providers:
    - type: sentence_transformers
    - type: openai
      id: openai-primary
      api_key_env: OPENAI_API_KEY
      extra:
        allowed_models:
          - gpt-4o
          - gpt-4o-mini
vLLM

Set type to vllm, and add VLLM_URL and VLLM_API_KEY to the Secret. VLLM_URL must be the full OpenAI-compatible base URL and end in /v1, for example, https://vllm.example.com/v1. Add VLLM_MAX_TOKENS or VLLM_TLS_VERIFY only when the defaults do not suit the endpoint. 

inference:
  providers:
    - type: sentence_transformers
    - type: vllm
      id: rhoai-vllm
      api_key_env: VLLM_API_KEY
      extra:
        base_url: ${env.VLLM_URL:=}
        max_tokens: ${env.VLLM_MAX_TOKENS:=4096}
        network:
          tls:
            verify: ${env.VLLM_TLS_VERIFY:=true}
Vertex AI

Set type to vertexai, and set VERTEX_AI_PROJECT, VERTEX_AI_LOCATION, and GOOGLE_APPLICATION_CREDENTIALS in the Secret. The GOOGLE_APPLICATION_CREDENTIALS value must be the in-container path of a separately mounted Google Cloud credential file. 

inference:
  providers:
    - type: sentence_transformers
    - type: vertexai
      id: vertex-gemini
      extra:
        project: ${env.VERTEX_AI_PROJECT:=}
        location: ${env.VERTEX_AI_LOCATION:=global}
        allowed_models:
          - google/gemini-2.5-flash

To enable more than one provider, combine the entries in a single inference.providers list. Keep every id unique, even when two entries use the same provider type. The following example enables two OpenAI providers and a vLLM provider while retaining the embedding provider that the default vector store uses: 

inference:
  providers:
    - type: sentence_transformers
    - type: openai
      id: openai-primary
      api_key_env: OPENAI_API_KEY
      extra:
        allowed_models:
          - gpt-4o-mini
    - type: openai
      id: openai-secondary
      api_key_env: OPENAI_SECONDARY_API_KEY
      extra:
        allowed_models:
          - gpt-4o
    - type: vllm
      id: rhoai-vllm
      api_key_env: VLLM_API_KEY
      extra:
        base_url: ${env.VLLM_URL:=}
        max_tokens: ${env.VLLM_MAX_TOKENS:=4096}
        network:
          tls:
            verify: ${env.VLLM_TLS_VERIFY:=true}

The paired Secret must define OPENAI_API_KEY, OPENAI_SECONDARY_API_KEY, VLLM_API_KEY, and a VLLM_URL value that ends in /v1. A user can then select models that any of these providers expose.

4.4. Disable Developer Hub Intelligent Assistant by using the Operator

Disable the Developer Hub Intelligent Assistant chat interface and stop associated container processes to remove the service from your Operator-backed deployment.

Prerequisites

  • You have access to the cluster where your instance is deployed.
  • You have cluster administrator privileges.

Procedure

  1. Open your Backstage custom resource (CR) YAML file.

  2. In the spec section, set the enabled flag to false for the intelligent-assistant flavour. This disables the chat interface and prevents the Operator from injecting unconfigured sidecar containers: 

    apiVersion: rhdh.redhat.com/v1alpha5
kind: Backstage
metadata:
  name: intelligent-assistant-disabled
spec:
  flavours:
    - name: intelligent-assistant
      enabled: false

  3. Apply the updated custom resource manifest to your cluster: 

    oc apply -f <backstage_cr_file>.yaml

Verification

  1. Log in to your console instance.
  2. Verify that the Intelligent Assistant button no longer appears on the home page.

4.5. Disable Developer Hub Intelligent Assistant by using the Helm chart

Disable the Developer Hub Intelligent Assistant chat interface and stop associated container processes to remove the service from your Helm-deployed environment.

Prerequisites

  • You have access to the cluster where your instance is deployed.

Verification

  2. Verify that the Intelligent Assistant button no longer appears on the home page.

4.6.1. Mirror Developer Hub Intelligent Assistant images for air-gapped environments

Mirror the required Developer Hub Intelligent Assistant container images and plugins to your local registry to provide chat assistance in an air-gapped environment.

The prepare-restricted-environment.sh script does not automatically parse Developer Hub Intelligent Assistant images from the bundle manifest, so mirror these images manually before running the script.

Prerequisites

  • You have a target mirror registry accessible to your disconnected cluster.
  • You authenticated to the Red Hat Container Registry and your target mirror registry.
  • You have configured image pull authentication for your mirror registry as described in Install Red Hat Developer Hub in an air-gapped environment with the Operator. The kubelet requires these credentials to pull all Red Hat Developer Hub container images, including the Developer Hub Intelligent Assistant sidecar images.

Procedure

  1. Extract the deployment configurations from the official Operator bundle: 

    BUNDLE_IMAGE="registry.redhat.io/rhdh/rhdh-operator-bundle:2.1"
CONTAINER_ID=$(podman create "${BUNDLE_IMAGE}")
podman cp $CONTAINER_ID:/manifests/rhdh-flavour-lightspeed-config_v1_configmap.yaml ./lightspeed-config.yaml
podman rm $CONTAINER_ID

  2. Identify the initialization and sidecar container image tags from the extracted configuration file: 

    LS_RAG_IMAGE=$(yq '.data["deployment.yaml"]' lightspeed-config.yaml | yq '.spec.template.spec.initContainers[] | select(.name == "init-rag-data") | .image')
LS_CORE_IMAGE=$(yq '.data["deployment.yaml"]' lightspeed-config.yaml | yq '.spec.template.spec.containers[] | select(.name == "lightspeed-core") | .image')

  3. Mirror the images to your internal registry by running the skopeo copy command: 

    skopeo copy docker://${LS_RAG_IMAGE} docker://<mirror_registry>/<ls_rag_repo>@<digest>
skopeo copy docker://${LS_CORE_IMAGE} docker://<mirror_registry>/<ls_core_repo>@<digest>

4.6.2. Mirror Developer Hub Intelligent Assistant images for Helm deployments on OpenShift Container Platform

Mirror the required Developer Hub Intelligent Assistant container images to your local registry by using the oc-mirror plugin when deploying the Helm chart on an OpenShift Container Platform cluster.

Prerequisites

  • You have a target mirror registry accessible to your disconnected OpenShift Container Platform cluster.
  • You authenticated to the Red Hat Container Registry and your target mirror registry.

The kubelet requires these credentials to pull all Red Hat Developer Hub container images, including the Developer Hub Intelligent Assistant sidecar images.

Procedure

  1. Identify the initialization and sidecar container images from the default values file of the chart: 

    helm show values redhat-developer-hub --repo https://charts.openshift.io/ --version 2.1.0 > values.default.yaml

LS_RAG_IMAGE=$(yq '.global.lightspeed.initContainer.image | .registry + "/" + .repository' values.default.yaml)

    apiVersion: mirror.openshift.io/v2alpha1

  additionalImages:

    - name: ${LS_CORE_IMAGE}:${LS_CORE_DIGEST}
  helm:
    repositories:
      - name: openshift-charts
        url: https://charts.openshift.io
        charts:
          - name: redhat-developer-hub
            version: "2.1"

5.1. Consolidated Developer Hub Intelligent Assistant configuration for stable model integration

In Red Hat Developer Hub (RHDH) 2.1, Developer Hub Intelligent Assistant sources all model, validation, tool, and vector-store settings from Lightspeed Core Service (LCORE), so you no longer configure or interact with Open GenAI Stack (OGX) directly.

Earlier releases exposed OGX configuration and used some OGX APIs directly. Because those APIs and configurations changed often, deployments broke and required expensive migrations. In RHDH 2.1, LCORE is the exclusive integration layer, and OGX is an internal implementation detail that is no longer customer-facing.

This change consolidates configuration into a single file and removes the direct OGX surface:

Unified configuration file
RHDH 1.10 used both a lightspeed-stack.yaml file and a separate config.yaml file. RHDH 2.1 uses one lightspeed-stack.yaml file. The config.yaml file and the llama_stack.library_client_config_path setting no longer apply.
Inference providers
You define each provider as an explicit entry under inference.providers, each with a unique id. The ENABLE_OPENAI, ENABLE_VLLM, ENABLE_VERTEX_AI, and ENABLE_OLLAMA switches no longer enable providers. A Secret supplies only credentials and endpoints.
Query validation
A top-level shields block defines the question-validity shield. You enable it by setting ENABLE_VALIDATION to question_validity, instead of the Llama Guard safety provider and registered shield resources used in 1.10.
Vector store
The file uses a singular top-level vector_store section. The installation program supplies the default configuration used for Notebooks.
Model Context Protocol (MCP) servers
The top-level mcp_servers section is unchanged from 1.10. You do not need to change existing entries.
Generated runtime file
LCORE creates the /tmp/.generated/run.yaml file at runtime from lightspeed-stack.yaml. Do not edit the generated file.

5.7. Inference provider configuration reference for Developer Hub Intelligent Assistant

To give Developer Hub Intelligent Assistant access to a model, define each inference provider as an entry under the top-level inference.providers section of the lightspeed-stack.yaml file.

The provider entry enables the provider. Adding an API key or an ENABLE_* variable to the Secret does not enable a provider on its own.

Keep the sentence_transformers provider when you add a large language model (LLM) provider. It supports the default embedding path that the shipped vector store uses.

Each LLM provider entry requires a unique id. The api_key_env field contains the name of an environment variable, not ${env…​} syntax and not the credential value. Lightspeed Core Service (LCORE) resolves the variable without exposing the key in the configuration file.

OpenAI

Set type to openai, and add OPENAI_API_KEY to the Secret. Use extra.allowed_models to limit model registration. If you omit it, the provider registers every model that is visible to the account. 

inference:
  providers:
    - type: sentence_transformers
    - type: openai
      id: openai-primary
      api_key_env: OPENAI_API_KEY
      extra:
        allowed_models:
          - gpt-4o
          - gpt-4o-mini
vLLM

Set type to vllm, and add VLLM_URL and VLLM_API_KEY to the Secret. VLLM_URL must be the full OpenAI-compatible base URL and end in /v1, for example, https://vllm.example.com/v1. Add VLLM_MAX_TOKENS or VLLM_TLS_VERIFY only when the defaults do not suit the endpoint. 

inference:
  providers:
    - type: sentence_transformers
    - type: vllm
      id: rhoai-vllm
      api_key_env: VLLM_API_KEY
      extra:
        base_url: ${env.VLLM_URL:=}
        max_tokens: ${env.VLLM_MAX_TOKENS:=4096}
        network:
          tls:
            verify: ${env.VLLM_TLS_VERIFY:=true}
Vertex AI

Set type to vertexai, and set VERTEX_AI_PROJECT, VERTEX_AI_LOCATION, and GOOGLE_APPLICATION_CREDENTIALS in the Secret. The GOOGLE_APPLICATION_CREDENTIALS value must be the in-container path of a separately mounted Google Cloud credential file. 

inference:
  providers:
    - type: sentence_transformers
    - type: vertexai
      id: vertex-gemini
      extra:
        project: ${env.VERTEX_AI_PROJECT:=}
        location: ${env.VERTEX_AI_LOCATION:=global}
        allowed_models:
          - google/gemini-2.5-flash

To enable more than one provider, combine the entries in a single inference.providers list. Keep every id unique, even when two entries use the same provider type. The following example enables two OpenAI providers and a vLLM provider while retaining the embedding provider that the default vector store uses: 

inference:
  providers:
    - type: sentence_transformers
    - type: openai
      id: openai-primary
      api_key_env: OPENAI_API_KEY
      extra:
        allowed_models:
          - gpt-4o-mini
    - type: openai
      id: openai-secondary
      api_key_env: OPENAI_SECONDARY_API_KEY
      extra:
        allowed_models:
          - gpt-4o
    - type: vllm
      id: rhoai-vllm
      api_key_env: VLLM_API_KEY
      extra:
        base_url: ${env.VLLM_URL:=}
        max_tokens: ${env.VLLM_MAX_TOKENS:=4096}
        network:
          tls:
            verify: ${env.VLLM_TLS_VERIFY:=true}

The paired Secret must define OPENAI_API_KEY, OPENAI_SECONDARY_API_KEY, VLLM_API_KEY, and a VLLM_URL value that ends in /v1. A user can then select models that any of these providers expose.

Chapter 7. Extend Intelligent Assistant with Bring Your Own Knowledge (BYOK)

Add your organization’s internal documentation as a retrieval-augmented generation (RAG) knowledge source so that Intelligent Assistant can search and cite your content alongside the default Red Hat Developer Hub (RHDH) product documentation.

7.1. Bring Your Own Knowledge (BYOK) for Intelligent Assistant

To ground AI answers in your organization’s own documentation, add an OGX vector store as a retrieval source. Developer Hub intelligent assistant then searches and cites your internal content alongside the default RHDH product documentation.

By default, Intelligent Assistant grounds AI responses in Red Hat Developer Hub (RHDH) product documentation. With BYOK, you can add knowledge sources such as internal runbooks, architecture guides, or custom API references, so that Intelligent Assistant can retrieve and cite content that is specific to your organization.

Note

This workflow is intended for RHDH administrators. For the current vector-store generation commands and prerequisites, see the rag-content README listed in the additional resources.

7.1.1. How BYOK works

The BYOK workflow has four parts:

  1. Prepare source documents and citation metadata.
  2. Generate embeddings and an OGX vector store with rag-content.
  3. Deliver the vector database and, when required, a local embedding model to the Intelligent Assistant runtime.
  4. Register the store as a retrieval source and verify it through the Intelligent Assistant.
Important

The embedding model and dimension used to generate the database must match the model and dimension in the runtime configuration. A mismatch prevents reliable retrieval and can stop the vector store from loading.

7.1.2. Retrieval source ordering and prioritization

The order of entries under rag.retrieval.inline.sources or rag.retrieval.tool.sources does not assign priority to the vector stores. For example, listing custom-docs before okp does not guarantee that content from custom-docs is returned first.

Intelligent Assistant supports per-store BYOK weighting only with Inline RAG. Set score_multiplier on each entry under rag.byok.stores to adjust its relative importance. Values greater than 1.0 boost that store’s results, while values less than 1.0 reduce them.

Inline RAG queries the configured BYOK stores, multiplies each raw relevance score by that store’s score_multiplier, merges the results, and ranks them by weighted score. Consequently, a store with a higher score_multiplier receives a boost regardless of where it appears in the sources list.

Tool RAG does not apply score_multiplier. It exposes the configured stores through the file_search tool. OGX searches them, merges their chunks, and ranks the combined results by the scores returned by the stores. Use Tool RAG when the model should decide when to search. Use Inline RAG when every request must retrieve context and you require configurable BYOK store weighting.

Note

score_multiplier applies only to BYOK stores. It does not weight OKP results, whose scores use a different scoring system. When you combine BYOK and OKP through Inline RAG, enable the supported reranker to normalize and rerank results across those sources.

7.3. Generate a vector store for BYOK RAG

Install the rag-content tooling, generate a portable OGX FAISS vector store from your custom documentation, and test retrieval before you deploy the store to Intelligent Assistant.

Prerequisites

  • You have prepared your content directory as described in Prepare the source documents for BYOK RAG.
  • You have a workstation with Git and uv installed.

Procedure

  1. Clone the rag-content repository and install its pinned dependencies: 

    $ git clone https://github.com/lightspeed-core/rag-content.git
$ cd rag-content
$ uv sync
    Tip

    Use a specific release or commit in repeatable production workflows. The generator, query helper, and runtime dependencies must be kept compatible.

  2. From the rag-content repository, generate a portable OGX FAISS vector store: 

    $ uv run python scripts/generate_embeddings.py \
  --folder /path/to/custom_docs \
  --output /path/to/vector_db/custom_docs \
  --index custom-docs \
  --vector-store llamastack-faiss \
  --model-dir "" \
  --model-name sentence-transformers/all-mpnet-base-v2 \
  --doc-type markdown \
  --chunk-size 512 \
  --chunk-overlap 128

    The llamastack-faiss value is retained as a compatibility name in the rag-content command-line interface. Current rag-content releases use OGX to create this store.

    Passing an empty value to --model-dir records the Hugging Face model ID rather than a workstation-specific model path. This makes the generated store portable. At runtime, the same model ID is resolved by the sentence_transformers provider.

    Note

    This model-ID configuration can require network access when the model is not already cached. For a disconnected deployment, package the embedding model and configure its runtime filesystem path as described in Deploy BYOK RAG in a disconnected environment.

  3. Confirm the output files. The output directory contains:

    • faiss_store.db: the vector store database required at runtime.
    • lightspeed-stack.yaml: an example Intelligent Assistant configuration generated for the store.
    • llama-stack.yaml: the OGX configuration used to create the store.

  4. Read the unique vector store ID from the generated configuration: 

    $ yq '.registered_resources.vector_stores[0].vector_store_id' \
  /path/to/vector_db/custom_docs/llama-stack.yaml

    Save this value. The runtime configuration must use the exact same ID.

  5. Test retrieval before deployment by using the query helper from the same rag-content checkout: 

    $ uv run python scripts/query_rag.py \
  --db-path /path/to/vector_db/custom_docs \
  --product-index custom-docs \
  --model-path "" \
  --top-k 5 \
  --query "Enter a question answered only by the custom documents" \
  --json

    Review the returned chunks, scores, titles, and source URLs. Use a question that contains a distinctive fact from the custom content so that the result is easy to distinguish from general model knowledge.

    Note

    Some combinations of OGX and rag-content can report that the vector store is already registered when query_rag.py opens a newly generated database. Do not edit the SQLite database manually. Use a compatible rag-content revision or continue validation through the deployed Intelligent Assistant vector store API, and report reproducible helper failures to the rag-content project.

7.7. Deploy BYOK RAG in a disconnected environment

Package the embedding model alongside the vector store and register the store with local runtime paths so that Intelligent Assistant can retrieve custom content without network access to Hugging Face.

A precomputed FAISS database contains the document embeddings, but Intelligent Assistant must still embed each incoming question before it can search that database. The runtime therefore requires the same embedding model and dimension that were used to generate the store. Supplying only faiss_store.db is not sufficient for a disconnected deployment.

The rag-content project provides a model-download helper and also bundles its default embedding model in its RAG tool image. The following upstream references are pinned to a specific revision so that the examples do not change unexpectedly:

  • rag-content model-download instructions
  • download_embeddings_model.py
  • Default model packaged by the RAG tool image

Prerequisites

  • You have generated a portable OGX FAISS vector store as described in Generate a vector store for BYOK RAG.
  • You have a connected build workstation that uses the same pinned rag-content checkout used to generate the vector store.
  • You have podman installed and a registry that is available to the disconnected OpenShift cluster.

Procedure

  1. On a connected build workstation, download the embedding model: 

    $ mkdir -p embeddings_model

$ uv run python scripts/download_embeddings_model.py \
  --local-dir ./embeddings_model \
  --hf-repo-id sentence-transformers/all-mpnet-base-v2

    The resulting directory includes the model weights, tokenizer, configuration, pooling, and normalization files needed by the sentence_transformers provider. Scan and transfer this directory according to your organization’s disconnected-content process.

    Note

    If the vector store is generated in a disconnected build environment, pass the local directory to --model-dir instead of an empty value. In either case, use the exact same model weights for generation and runtime. Changing the model requires regenerating the vector store.

  2. Place the generated vector_db directory and downloaded embeddings_model directory in the container build context: 

    byok-image/
  Containerfile
  vector_db/
    custom_docs/
      faiss_store.db
  embeddings_model/
    model.safetensors
    config.json
    tokenizer.json
    ...

    FROM registry.access.redhat.com/ubi9/ubi-minimal:latest

RUN chgrp -R 0 /byok && chmod -R g=u /byok

$ podman push registry.example.com/rhdh/byok-content:1.0.0

7.11. Resolve common BYOK RAG problems

Resolve common errors that occur when you configure or use a Bring Your Own Knowledge (BYOK) RAG knowledge source with Intelligent Assistant.

7.11.1. The store does not load

Symptom: Intelligent Assistant fails to load the vector store at startup or on the first query.

Resolution:

  • Confirm that db_path is the path inside the Intelligent Assistant container, not the path used on the generation workstation or inside the delivery image.
  • In a disconnected environment, confirm that embedding_model is the local path inside the Intelligent Assistant container rather than only a Hugging Face model ID.
  • Confirm that the init container copied the complete model directory, including weights, tokenizer, model configuration, pooling, and normalization files.
  • Confirm that vector_db_id exactly matches the generated ID.
  • Confirm that the database file is present, non-empty, and readable by the container user.
  • Review init-container and Intelligent Assistant startup logs.

7.11.2. Queries return irrelevant chunks

Symptom: The knowledge source is configured and citations appear, but retrieved content is empty or unrelated.

Resolution:

  • Confirm that the generation and runtime embedding models are identical.
  • Confirm that the configured embedding dimension matches the model.
  • Improve document headings and remove navigation or boilerplate text that dominates the content.
  • Adjust chunk size and overlap, regenerate the store, and compare results with representative test questions.

7.11.3. Citations are missing or incorrect

Symptom: Responses do not include the expected source title or URL, or cite the wrong source.

Resolution:

  • Confirm that each source document contains valid title and url frontmatter.
  • Inspect query results to ensure that title and URL metadata were stored with the chunks.

8.4. Configure rate limits for the Intelligent Assistant

Configure per-user rate limits for the Intelligent Assistant to prevent abuse, control large language model (LLM) inference costs, and protect backend resources.

Rate limiting is active by default. Requests are tracked per authenticated user entity reference within a fixed 1-minute window. The Intelligent Assistant applies rate limits by tier:

Expensive (default: 25 requests/min/user)
Applies to POST /v1/query (LLM inference), notebook document uploads, and Retrieval Augmented Generation (RAG) queries.
General (default: 200 requests/min/user)
Applies to all other authenticated endpoints, including conversation listing, Model Context Protocol (MCP) server management, feedback, and notebook session create, read, update, and delete operations.
Excluded (no limit)
Applies to health check endpoints (/health, /notebooks/health).

Prerequisites

  • You have deployed and configured the Intelligent Assistant instance.
  • You have administrative access to the RHDH host platform filesystem.

Procedure

  1. In your app-config.yaml file, add or modify the rateLimit block under the intelligent-assistant section: 

    intelligent-assistant:
  rateLimit:
    expensive:
      max: 25
    general:
      max: 200
    expensive.max
    Maximum requests per minute per user for expensive endpoints such as LLM inference. Set to 0 to disable rate limiting for this tier.
    general.max

    Maximum requests per minute per user for general endpoints. Set to 0 to disable rate limiting for this tier.

    The following example shows a tightened configuration for a small deployment with limited LLM resources: 

    lightspeed:
  rateLimit:
    expensive:
      max: 10
    general:
      max: 50
  2. Save the file.
  3. Restart the RHDH service to apply the updated configuration.

Verification

  1. Log in to RHDH and submit requests to the Intelligent Assistant chat interface that exceed the configured expensive limit.

9.2. Configure Agent Skills for Intelligent Assistant

Prerequisites

  • You have administrative access to the RHDH deployment.
  • You store your skills in a Git repository that the cluster can access, or you have the skill files available to store in a ConfigMap.

Procedure

  1. In your custom lightspeed-stack.yaml file, add the mounted directory under skills.paths: 

    skills:
  paths:
    - /app-root/skills

    A path can identify either a single skill directory or a parent directory that contains multiple skill directories.

  2. Make the skills directory available to the lightspeed-core container.

    Note

    If you already mount a volume that contains your skills into the lightspeed-core container, you can skip the init-container configuration. Mount the existing volume at /app-root/skills, or update skills.paths to match its mount path.

    Otherwise, configure the volume, init container, and mount before you deploy or upgrade RHDH. This configuration ensures that the skills are present when the lightspeed-core container starts.

    1. For an Operator installation, add a strategic merge patch to the Backstage custom resource (CR): 

      apiVersion: rhdh.redhat.com/v1alpha5
kind: Backstage
metadata:
  name: <rhdh_instance_name>
spec:
  deployment:
    patch:
      spec:
        template:
          spec:
            volumes:
              - name: lightspeed-skills
                emptyDir: {}
            initContainers:
              - name: fetch-lightspeed-skills
                image: <image_with_git_client>
                imagePullPolicy: IfNotPresent
                command:
                  - /bin/sh
                  - -ec
                args:
                  - |
                    git clone --depth 1 --branch <repository_ref> \
                      <skills_repository_url> /work/.source
                    test -d /work/.source/skills
                    cp -R /work/.source/skills/. /work/
                    rm -rf /work/.source
                volumeMounts:
                  - name: lightspeed-skills
                    mountPath: /work
            containers:
              - name: lightspeed-core
                volumeMounts:
                  - name: lightspeed-skills
                    mountPath: /app-root/skills

    2. For a Helm installation, add the following configuration to the values.yaml file. The chart appends these entries to the generated pod specification: 

      intelligentAssistant:
  enabled: true
  core:
    extraVolumeMounts:
      - name: lightspeed-skills
        mountPath: /app-root/skills

extraVolumes:
  - name: lightspeed-skills
    emptyDir: {}

extraInitContainers:
  - name: fetch-lightspeed-skills
    image: <image_with_git_client>
    imagePullPolicy: IfNotPresent
    command:
      - /bin/sh
      - -ec

      - |
        git clone --depth 1 --branch <repository_ref> \
          <skills_repository_url> /work/.source
        test -d /work/.source/skills
        cp -R /work/.source/skills/. /work/
        rm -rf /work/.source

      - name: lightspeed-skills
        mountPath: /work

      Replace the following values:

      <image_with_git_client>
      An approved image that contains Bash and Git.
      <skills_repository_url>
      The URL of the repository that contains the skills.

      The branch or tag to retrieve.

10.2. Enable data persistence for Intelligent Assistant Notebooks

Notebook embeddings are stored in a FAISS vector store, which Intelligent Assistant persists to a SQLite file on disk. By default, that file lives on an ephemeral emptyDir volume, so the system clears it when the pod restarts or reschedules.

To retain Notebook documents and embeddings across restarts, move the FAISS store onto a Persistent Volume by pointing the notebooks vector store provider at a persistent mount and backing that mount with a Persistent Volume Claim (PVC). The store remains an on-disk FAISS file; only the volume behind it changes.

Important

Depending on your installation method, note the following constraints:

  • Helm chart: The notebooks vector store provider defaults to an ephemeral path. Moving the provider path to a custom PVC mount (like /var/lib/lightspeed-data) works, but alternatively, you can use the chart’s native runtimeVolume.type: persistentVolumeClaim configuration.
  • Operator: The Operator currently mounts configuration via annotated config maps and does not expose a PVC option. Modifying the deployment manifest manually (as shown in this procedure) is unsupported for Operator installs, as changes will be reverted during operator reconciliation.

Prerequisites

  • By using the OpenShift CLI (oc), you have access, with developer permissions, to the OpenShift Container Platform cluster that contains your Developer Hub instance.
  • You have authored and provisioned a custom config map for your deployment. For more information, see link:Provision your custom Red Hat Developer Hub configuration.
  • A Persistent Volume Claim (PVC) is provisioned in the namespace of your Intelligent Assistant deployment. You can use any name for the PVC. The examples in this procedure use intelligent-assistant-notebooks-pvc.

Procedure

  1. In your lightspeed-stack.yaml config map, point the notebooks vector store provider at a path on the persistent mount. The provider stays faiss, so the FAISS index continues to persist as an on-disk file: 

    vector_store:
  default_provider: notebooks
  providers:
    - id: notebooks
      type: faiss
      embedding_model: nomic-ai/nomic-embed-text-v1.5
      embedding_dimension: 768
      config:
        path: /var/lib/lightspeed-data/vector_db/notebooks/faiss_store.db

  2. Update your deployment manifest to create the directory on the volume and mount the PVC into the Intelligent Assistant container. The config map mounts are already defined by the deployment and are unchanged: 

    spec:
  template:
    spec:
      securityContext:
        fsGroup: 1000
      initContainers:
        - name: init-notebooks-storage
          image: registry.access.redhat.com/ubi9/ubi-minimal
          command:
            - sh
            - -c
            - mkdir -p /var/lib/lightspeed-data/vector_db/notebooks
          volumeMounts:
            - name: intelligent-assistant-notebooks
              mountPath: /var/lib/lightspeed-data
      containers:
        - name: lightspeed-core
          volumeMounts:
            - name: intelligent-assistant-notebooks
              mountPath: /var/lib/lightspeed-data
      volumes:
        - name: intelligent-assistant-notebooks
          persistentVolumeClaim:
            claimName: intelligent-assistant-notebooks-pvc
  3. Apply the updated configuration and restart the service.

Verification

  1. In Red Hat Developer Hub, create a Notebook and upload a test document.
  2. Send a message to the virtual assistant and verify that the response is based on the document.

  3. Restart the pod: 

    $ oc delete pod <pod_name>

  5. Verify that the Notebook and the uploaded file are still accessible.

11.2. Enable query validation to block off-topic AI responses

Enable the question-validity shield to classify each prompt before Developer Hub Intelligent Assistant answers it, so that off-topic or harmful prompts never reach your answering model.

In RHDH 2.1, Developer Hub Intelligent Assistant validates prompts through a single question-validity shield that Lightspeed Core Service (LCORE) defines in the lightspeed-stack.yaml configuration file. This shield replaces the Llama Guard safety provider, registered shield resources, and run.yaml overrides used in earlier releases. Do not edit Open GenAI Stack (OGX) files or the generated run.yaml file to change validation behavior.

The shipped lightspeed-stack.yaml file includes the shield in a disabled state. You enable or disable the shield through environment variables in the Kubernetes Secret that LCORE reads. When you enable the shield, LCORE sends each prompt to the validation model, which classifies the prompt as allowed or rejected.

Prerequisites

  • You have an inference provider configured and enabled in the inference.providers section of your lightspeed-stack.yaml file.
  • You can edit the Kubernetes Secret that supplies environment variables to the lightspeed-core container.

Procedure

  1. To enable query validation, add the following keys to the Secret that LCORE reads: 

    stringData:
  ENABLE_VALIDATION: question_validity
  VALIDATION_PROVIDER: <provider_type>
  VALIDATION_MODEL_NAME: <model_name>

    where:

    ENABLE_VALIDATION
    Specifies whether the shield is enabled. You must set the value to question_validity. A nonempty value such as true does not enable the shield in RHDH 2.1.
    VALIDATION_PROVIDER
    Specifies the type of the inference provider that runs the classification, for example, openai or vllm. A provider of this type must be enabled in inference.providers.
    VALIDATION_MODEL_NAME

    Specifies the model that classifies each prompt. If the provider defines allowed_models, include this model in that list.

    For example, to run classification on an openai provider with the gpt-4o-mini model, set the following values: 

    stringData:
  ENABLE_VALIDATION: question_validity
  VALIDATION_PROVIDER: openai
  VALIDATION_MODEL_NAME: gpt-4o-mini

  2. To keep query validation disabled, leave ENABLE_VALIDATION unset, or set it to disabled: 

    stringData:
  ENABLE_VALIDATION: __disabled__
    Important

    Running without query validation increases the risk of off-topic or harmful model output. Disable validation only in secure development environments.

  3. Apply the updated Secret, and then restart the LCORE service so that the container reads the new environment variables.

Verification

  1. Open the Intelligent Assistant and submit a development question, for example, How do I create a software template in RHDH?. Confirm that the assistant answers the question.
  2. Submit a clearly unrelated question, for example, What is a good recipe for pizza?. Confirm that the assistant rejects the question when validation is enabled.

Improve assistant accuracy

Important
