Preface

You can migrate a Red Hat Developer Hub (RHDH) instance from version 1.10 to version 2.1.

Chapter 1. Assess the impact of breaking changes before migrating

When you are planning an upgrade from Red Hat Developer Hub 1.10 to 2.1, you want to understand every breaking change and its impact on your deployment, so you can scope the work, assign it to the right people, and avoid unexpected failures during migration.

This phase helps you review the breaking changes, inventory your current configuration, and complete a pre-upgrade checklist to prepare for the migration.

1.1. Migrating from RHDH 1.10 to 2.1

RHDH 2.1 introduces breaking changes to Helm charts, custom plugins, RBAC policies, AI assistant settings, container images, and plugin distribution. None provide a backward-compatible shim and some fail silently, so review the changes that apply to your deployment.

1.1.1. Breaking changes quick reference

The following table summarizes the breaking changes in RHDH 2.1 and links to the procedure that resolves each one. Use it to scope the work and confirm that you have addressed every change that applies to your deployment.

Breaking changeImpactAction

Bundled plugin wrappers are removed

The RHDH image no longer ships bundled plugin wrappers. A plugin that uses a local wrapper path, such as package: ./dynamic-plugins/dist/<plugin-name>, no longer resolves after the upgrade.

Must fix. Replace each local wrapper path with an OCI reference. See Migrate plugin references to OCI format.

New Frontend System (NFS) hard cut-over

The Old Frontend System (OFS) is removed. Custom plugins that use OFS APIs stop working silently. Red Hat supported plugins work with both systems; only custom plugins are affected.

Must fix for custom plugins. Rewrite custom plugins for the NFS before you upgrade.

Container images renamed

The RHEL 9 base images are replaced with RHEL 10 images, and the image names change. Disconnected environments that mirror by image name receive 404 errors.

Must fix for disconnected environments. Update your mirrored image references to the new names.

RBAC permissions renamed

CRUD-style permission names are replaced with behavior-linked names. Old permission names fail silently, and users lose access with no error.

Must fix. Update your RBAC policies to the new permission names.

Lightspeed rebranded to the intelligent assistant

Plugin names, configuration keys, route paths, and permissions change. Any configuration that references lightspeed is silently ignored.

Must fix. Rename the affected configuration keys and permissions.

Llama Stack removed

The Llama Stack integration is removed. Lightspeed Core Service (LCORE) provides equivalent API gateway functionality.

Must fix if you use Llama Stack. Reconfigure your deployment to point to LCORE.

Standalone Helm chart

The RHDH 2.1 Helm chart is a standalone chart. Running helm upgrade from a 1.x release is not supported.

Must fix for Helm deployments. Export your values, uninstall the 1.x release, and perform a fresh install.

Chapter 2. Prepare custom plugins for the New Frontend System

When you have custom plugins built on the old frontend system, you want to rewrite them for the New Frontend System before the platform upgrade happens, so you can deploy them immediately on the 2.1 platform without downtime or rework.

This phase helps you understand the New Frontend System changes, migrate your custom plugin code, and test the migrated plugins before the platform upgrade.

2.1. New Frontend System changes in RHDH 2.1

Red Hat Developer Hub 2.1 removes the old frontend system (OFS) and requires all plugins to use the New Frontend System (NFS). Red Hat supported plugins are compatible with both systems, but custom plugins built on OFS APIs stop working silently after the upgrade.

2.2. Migrate custom plugins to the New Frontend System

Custom plugins built with Old Frontend System (OFS) APIs must be rewritten to use New Frontend System (NFS) extensions and re-exported as dynamic plugins before you can deploy them on Red Hat Developer Hub 2.1.

Prerequisites

  • You have access to the source code of your custom plugins.
  • You have Red Hat Developer Hub Local or a separate Red Hat Developer Hub instance for testing migrated plugins.

Procedure

  1. Rewrite OFS plugin registration to NFS extensions.

    1. Replace dynamicRoutes, mountPoints, routeBindings, appIcons, and apiFactories with their NFS equivalents.
    2. Refer to the OFS to NFS configuration key mapping for the complete mapping.
  2. Re-export your plugin as a dynamic plugin.
  3. Test your migrated plugin using Red Hat Developer Hub Local or a separate Red Hat Developer Hub instance.

Verification

  • Confirm that the plugin loads without errors and all functionality works as expected.

Chapter 3. Reinstall the platform with the standalone Helm chart

When you are ready to move your production Red Hat Developer Hub instance to 2.1, you want to export your current configuration, uninstall the 1.x release, and install the new standalone Helm chart, so you can run the platform on the updated infrastructure with the correct container images.

This phase helps you understand the Helm chart changes, translate your configuration values, update container image references, and perform the platform reinstallation.

3.1. Helm chart changes in RHDH 2.1

The Red Hat Developer Hub 2.1 Helm chart is a standalone chart that replaces the 1.x chart structure. Running helm upgrade from 1.x is not supported—you must uninstall the 1.x release and perform a fresh install.

3.2. Migrate Helm chart values to RHDH 2.1

To migrate your Helm chart configuration to Red Hat Developer Hub 2.1, export your current Helm values, translate the configuration keys to the new format, and install the 2.1 chart.

Prerequisites

  • You have completed the pre-upgrade checklist and created a backup of your database.
  • You have migrated your custom plugins to the New Frontend System.

Procedure

  1. Export your current Helm values: 

    $ helm get values <release-name> -n <namespace> > values-1.x.yaml
  2. Translate your configuration keys using the Helm chart values mapping.
  3. Update your container image references from RHEL 9 to RHEL 10 names using the container image renames reference.

  4. Uninstall the 1.x release: 

    $ helm uninstall <release-name> -n <namespace>

  5. Install the 2.1 chart with your translated values: 

    $ helm install <release-name> <chart-repo>/redhat-developer-hub -n <namespace> -f values-2.1.yaml

Verification

  • Verify that the Red Hat Developer Hub platform starts without errors.

Chapter 4. Update permissions and configuration to match renamed services

When the platform is running on 2.1, you want to update your RBAC policies, AI assistant configuration, and plugin distribution references to use the new names and formats, so you can restore access for your users and ensure the platform recognizes your existing settings.

This phase helps you migrate AI assistant configuration, update RBAC policies, reconfigure Llama Stack connections, and replace plugin package references with OCI artifact URLs.

4.1. AI assistant changes in RHDH 2.1

Red Hat Developer Hub 2.1 renames the AI assistant feature from Lightspeed to intelligent assistant. Configuration keys, RBAC permission names, and route paths all change. Llama Stack integration is removed and replaced by LCORE (Lightspeed Core Service).

4.2. Migrate AI assistant configuration

To migrate your AI assistant configuration to Red Hat Developer Hub 2.1, rename configuration keys from lightspeed to intelligent-assistant, update RBAC policies to use the new behavior-linked permission names, and reconfigure Llama Stack connections to point to LCORE.

Prerequisites

  • You have completed the platform migration and installed the 2.1 Helm chart.
  • You have access to your Red Hat Developer Hub configuration files and RBAC policies.

Procedure

  1. Rename AI assistant configuration keys:

    1. Replace all instances of lightspeed with intelligent-assistant in your configuration files.
    2. Refer to the AI permissions mapping for the complete list of changes.

  2. Update RBAC policies:

    1. Replace CRUD-style permission names (for example, lightspeed.read) with behavior-linked permission names (for example, intelligent-assistant.chat).
    2. Update route path references from /lightspeed to /intelligent-assistant.

  3. Reconfigure Llama Stack connections:

    1. Update any Llama Stack connection settings to point to LCORE instead.

Verification

  1. Verify that AI assistant features respond as expected.
  2. Confirm that RBAC policies grant the correct access.

4.4. Plugin distribution changes in RHDH 2.1

In RHDH 2.1, bundled plugin wrappers are removed from the image and plugins are consumed only as Open Container Initiative (OCI) artifacts. A plugin that references a wrapper by a local path no longer resolves after you upgrade.

4.4.1. Bundled plugin wrappers are removed

In earlier releases, the RHDH image shipped a set of bundled plugin wrappers that you could reference by using a local path, for example package: ./dynamic-plugins/dist/<plugin-name>. RHDH 2.1 no longer ships these wrappers in the image.

As a result, any plugin entry that uses a local wrapper path no longer resolves after the upgrade. This applies to local paths wherever they appear, including the following locations:

  • The dynamic-plugins.yaml file
  • The global.dynamic.plugins values in your Helm chart configuration
  • The dynamicPlugins configuration in your Operator custom resource (CR)
Important

The package: ./dynamic-plugins/dist/<plugin-name> pattern, and any equivalent local wrapper path, is no longer valid in RHDH 2.1. Plugins that still use these paths fail to load after the upgrade. You must update each entry to an OCI reference before you upgrade. For the required steps, see Migrate plugin references to OCI format.

4.4.2. Plugins are consumed as OCI artifacts

In RHDH 2.1, you reference a plugin by using one of the following package formats:

package: oci://<image-reference>
References a plugin that is packaged as a pinned OCI image, for example oci://quay.io/<account-name>/<image-name>:<tag>!<plugin-name>.
package: ref://<plugin-name>
References a catalog plugin by using a stable, name-based reference. RHDH resolves the reference to the corresponding OCI artifact.

The default plugins that ship with RHDH 2.1, and the catalog references that RHDH resolves, are OCI-based.

4.4.3. The plugin catalog is OCI-only

The plugin catalog, the Package entities that it exposes, and the generated plugin tables in the documentation list OCI artifacts only. Bundled wrapper paths are no longer published as valid artifacts and are not available as catalog references.

When you look up a plugin to migrate, use the OCI artifact reference that the plugin catalog or the generated plugin tables provide. Do not expect a local wrapper path to be listed.

4.4.4. Janus IDP wrappers are discontinued

The Janus IDP wrapper packages are discontinued. A configuration that installs a plugin from a Janus IDP wrapper package name, such as @janus-idp/<plugin-name>, no longer resolves. Replace these references with the OCI artifact for the equivalent RHDH 2.1 plugin. For a mapping of discontinued wrapper package names to their RHDH 2.1 OCI references, see Janus IDP wrapper to RHDH 2.1 OCI plugin mapping.

Note

This change is a removed function in RHDH 2.1: the RHDH image no longer ships bundled plugin wrappers, and the default plugins and catalog references are OCI-based. For the complete list of removed functions, see the RHDH 2.1 release notes.

4.5. Migrate plugin references to OCI format

Because RHDH 2.1 removes the bundled plugin wrappers from the image, replace every local wrapper path in your plugin configuration with an Open Container Initiative (OCI) reference, by using either an oci:// reference or a ref://<plugin-name> reference.

Prerequisites

  • You identified every plugin entry that uses a local wrapper path or a Janus IDP wrapper package name. These entries can appear in the dynamic-plugins.yaml file, in the global.dynamic.plugins values of your Helm chart configuration, or in the dynamicPlugins configuration of your Operator custom resource (CR).
  • You have the OCI artifact reference for each plugin. Use the reference that the plugin catalog or the generated plugin tables provide. For discontinued Janus IDP wrappers, see Janus IDP wrapper to RHDH 2.1 OCI plugin mapping.

Procedure

  1. For each plugin that uses a local wrapper path, replace the package value with an OCI reference.

    • To reference a plugin that is packaged as a pinned OCI image, use an oci:// reference.
    • To reference a catalog plugin by using a stable, name-based reference, use a ref://<plugin-name> reference.

    For example, the following plugin entry uses a local wrapper path, which is no longer valid in 2.1: 

    plugins:
  - package: ./dynamic-plugins/dist/<plugin-name>
    disabled: false
    pluginConfig: {}

    To reference the same plugin as a pinned OCI image, use an oci:// reference: 

    plugins:
  - package: oci://quay.io/<account-name>/<image-name>:<tag>!<plugin-name>
    disabled: false
    pluginConfig: {}

    To reference the same plugin as a catalog plugin, use a ref://<plugin-name> reference: 

    plugins:
  - package: ref://<plugin-name>
    disabled: false
    pluginConfig: {}
  2. If you install plugins from Janus IDP wrapper packages, replace each @janus-idp/<plugin-name> reference with the OCI artifact for the equivalent RHDH 2.1 plugin.
  3. Apply the same change in every location that references plugins by a local path, including the dynamic-plugins.yaml file, the Helm chart values, and the Operator CR.
  4. For disconnected environments, mirror the OCI artifacts to your internal registry and update your references to point to the mirrored location.

Verification

  1. Start RHDH and confirm that it starts without plugin resolution errors.
  2. Confirm that all expected plugins are loaded. In the install-dynamic-plugins init container log, verify that each migrated plugin is installed and that no entry reports a missing local wrapper path.

Chapter 5. Verify your migration and resolve common issues

When you have completed all migration steps, you want to verify that the platform and plugins are functioning correctly and quickly diagnose any issues, so you can confirm the upgrade is complete and your teams can resume normal work.

This phase helps you verify platform functionality, confirm RBAC policies, test AI assistant features, and troubleshoot common post-migration issues.

5.1. Common migration issues for RHDH 2.1

After completing all migration steps, some issues—such as silently ignored permissions or missing plugin registrations—may not produce error messages and require targeted verification.

Rename configuration keys using the AI assistant migration procedure
