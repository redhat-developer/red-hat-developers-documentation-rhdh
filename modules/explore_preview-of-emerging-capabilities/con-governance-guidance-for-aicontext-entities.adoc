= Governance guidance for AIContext entities

[role="_abstract"]
As a Platform Engineer, you can use `AIContext` entities to publish governed, authoritative AI content assets for your organization. Use the following guidance to manage the ownership, scope, and availability of AI content assets.

== Ownership and access control
Each `AIContext` entity declares an owner in the `spec.owner` field. Ownership and access are enforced by the existing catalog role-based access control (RBAC) model. No RBAC controls are specific to the `AIContext` kind; the permissions that govern other catalog entities apply to `AIContext` entities in the same way.

== Scope
Use the `spec.scope` field to indicate the organizational reach of an asset: `organization`, `product`, or `team`. Developers can use the scope to identify the assets that are relevant to their context.

== Lifecycle
Because the `AIContext` kind is experimental, set `lifecycle: experimental` until the schema stabilizes. This value signals to developers that the asset definition might change.

== Air-gapped environments
`AIContext` entities are fully supported in air-gapped environments:

* The `catalog-info.yaml` file is ingested from your internal source control.
* OCI image references can point to internal registries, such as an on-premise Quay.io instance or an internal container registry.

Because the catalog records the asset location only and does not pull or run OCI image content, external connectivity is not required for catalog indexing.

== Promoting best practices
To encourage adoption, publish {company-name}-curated or organization-curated reference `AIContext` entities, and provide a Software Template that helps teams create new entities with valid examples for both source repository and OCI image assets.
