= Troubleshoot login failed errors

[role="_abstract"]
When a user cannot sign in to {product-short}, the sign-in page displays a "Login failed" error message, or, if no authentication provider is available, a descriptive error on the sign-in page itself.
The following sections describe common login errors and their solutions.

== Login failed: unable to resolve user identity

----
Login failed; caused by Error: Failed to sign-in, unable to resolve user identity. Please verify that your catalog contains the expected User entities that would match your configured sign-in resolver.
----

This error indicates that the user signing in does not match a user entity in the {product-short} software catalog.

To resolve this issue:

. Check that the corresponding catalog provider plugin is set up correctly and is successfully syncing users and groups into the catalog.
+
In the backend logs, look for a successful synchronization message such as:
+
[source]
----
catalog info Read 114 GitHub users and 22 GitHub groups in 3.4 seconds. Committing...
catalog info Committed 114 GitHub users and 22 GitHub groups in 0.0 seconds.
----

. If users and groups have been ingested into the catalog, verify that the sign-in resolver used (default or configured) matches the correct user attributes.
. Optionally, use guest login to look into the user entity in the catalog and verify the attributes.

== Login failed: provider not configured to support sign-in

----
Login failed; caused by Error: The <providerId> provider is not configured to support sign-in.
----

This error indicates that the authentication provider is configured as an auxiliary provider, not for primary sign-in.

The `disableIdentityResolution` setting is removed in {product-short} 2.1.
To configure a provider as an auxiliary provider instead of a primary sign-in provider, omit the `signIn.resolvers` field for that provider in your `{my-app-config-file}` file.

To resolve this issue:

* In your `{my-app-config-file}` file, ensure that `signIn.resolvers` is configured for your primary sign-in authentication provider.

== Login failed: authentication provider is not registered

// EDITOR NOTE (RHIDP-5489, pending engineer confirmation): the exact error text that the
// sign-in page or backend log displays for this scenario is unconfirmed. The following
// description reflects the `IMPORTANT` admonition in
// ref-authentication-provider-dynamic-plugin-packages.adoc, not a literal, verified error
// message.

If a provider is configured under `auth.providers` in your `{my-app-config-file}` file but its dynamic plugin is not installed or is disabled, {product-short} does not register the provider.
Users cannot sign in with that provider, even though it appears in your configuration.

To resolve this issue:

* Install the authentication provider dynamic plugin for the provider, and set `disabled` to `false` for its package in your `dynamic-plugins.yaml` file.
For more information, see {authentication-book-link}#authentication-provider-dynamic-plugin-packages_enable-authentication-with-your-identity-provider[the authentication provider dynamic plugin packages reference].
* Restart the {product-short} application to apply the changes.

== Login failed: user profile does not contain an email

----
Login failed, user profile does not contain an email
----

This error indicates that the authentication client does not have permission to read the user's email from the identity provider.

To resolve this issue:

* Grant the necessary email-reading permissions to the authentication client in the identity provider.
* Or, use a sign-in resolver that does not rely on email, such as `preferredUsernameMatchingUserEntityName` instead of `emailMatchingUserEntityProfileEmail`.

== Login failed: no authentication provider available

// EDITOR NOTE (RHIDP-5489, pending engineer confirmation): the exact message that the
// sign-in page displays for this scenario is unconfirmed. This entry reflects the
// engineers' draft statement that the previous automatic fallback to GitHub or the guest
// user is removed in {product-short} 2.1, but the literal on-screen error text has not
// been verified against this repo's content.

In previous releases, if no authentication provider was configured or resolvable, the sign-in page silently fell back to GitHub or the guest user.
In {product-short} 2.1, this fallback is removed.
If no provider is configured under `auth.providers`, or none of the configured providers can be resolved, the sign-in page displays a descriptive error instead.

To resolve this issue:

* Configure at least one authentication provider under `auth.providers` in your `{my-app-config-file}` file, install its dynamic plugin, and enable it in your `dynamic-plugins.yaml` file.
For more information, see {authentication-book-link}#authentication-provider-dynamic-plugin-packages_enable-authentication-with-your-identity-provider[the authentication provider dynamic plugin packages reference].
