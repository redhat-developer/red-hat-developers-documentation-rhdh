= Deploy custom dynamic plugins

[role="_abstract"]
To add a custom dynamic plugin to {product}, register its exported package in `dynamic-plugins.yaml` or reference its OCI image. In {product} 2.1, the application discovers front-end extensions from the plugin's NFS feature export without `dynamicPlugins.frontend` wiring.

.Prerequisites

* You have exported a custom plugin that uses the new front-end system. For plugin development steps, see {configuring-book-link}#migrate-custom-plugins-to-ensure-compatibility-after-upgrade_migrate-to-the-front-end-system-to-use-blueprint-based-dynamic-routing[Migrate custom plugins to ensure compatibility after upgrade].
* If you use an OCI image, you have made the image accessible to {product} or configured a pull secret for its registry. See {installing-and-viewing-plugins-book-link}#load-a-plugin-packaged-as-an-oci-image_install-plugins-in-rhdh[Loading a plugin packaged as an OCI image].

.Procedure

. Add the plugin package to `dynamic-plugins.yaml`. For example:
+
[source,yaml,subs="+quotes"]
----
plugins:
  - package: oci://quay.io/_<namespace>_/simple-example:v0.1.0
    enabled: true
----
+
For local {product-local-very-short} testing, use `dynamic-plugins.override.yaml` and a local package path instead of the OCI image reference.
. If you need to customize an extension that the plugin provides, set its extension ID under `app.extensions` in your `{my-app-config-file}` file. Do not copy old `dynamicRoutes` or `mountPoints` blocks into the plugin installation configuration. See {configuring-book-link}#configuration-key-mapping-from-old-to-new-front-end-system_migrate-to-the-front-end-system-to-use-blueprint-based-dynamic-routing[Configuration key mapping from old to new front-end system].

.Verification
After restarting {product-very-short}, confirm that the plugin's page or component is displayed in the application.
