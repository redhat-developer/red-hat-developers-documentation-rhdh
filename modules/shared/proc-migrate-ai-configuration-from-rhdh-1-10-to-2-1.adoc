= Migrate AI configuration from {product-very-short} 1.10 to 2.1

[role="_abstract"]
Update your AI backend configuration to align with the {lcs-name} ({lcs-short}) conventions introduced in {product} ({product-very-short}) 2.1, which replaces the Llama Stack backend.

.Prerequisites

* You have a running {product-very-short} 1.10 instance with AI features enabled.
* You have access to your deployment manifests, configuration files, and RBAC policy files.

.Procedure

. Update the backend container name in your deployment manifests by replacing `llama-stack` with `lightspeed-core`:
+
[source,yaml]
----
containers:
  - name: lightspeed-core
----

. Move your backend configuration from the Llama Stack `run.yaml` file to the `lightspeed-stack.yaml` file that {lcs-short} reads from a config map. Define your inference providers in the `inference.providers` section of `lightspeed-stack.yaml`, and do not edit the generated `run.yaml` file. For the supported providers and their requirements, see xref:large-language-model-llm-requirements_enable-ai-assistance-for-developers[Large language model (LLM) requirements].

. Reconfigure safety validation. {product-very-short} 2.1 replaces the Llama Guard safety provider and `run.yaml` shield overrides with a question-validity shield that you enable through environment variables in the Kubernetes Secret that {lcs-short} reads. For the procedure, see xref:configure-safety-guards-in-rhdh_intelligent-assistant-ai-virtual-assistant-capabilities[Enable query validation to block off-topic AI responses].

. If you persisted {ia-short} Notebook data on a Llama Stack path, point the `notebooks` vector store provider in `lightspeed-stack.yaml` at a persistent mount, such as `/var/lib/lightspeed-data`, backed by a Persistent Volume Claim (PVC). For the procedure, see xref:enable-data-persistence-for-intelligent-assistant-notebooks_build-a-private-knowledge-base-with-intelligent-assistant-notebooks[Enable data persistence for {ia-short} Notebooks].

. Update your RBAC policies to use the new permission identifiers. {product-very-short} 2.1 replaces the `lightspeed.{asterisk}` permission namespace with `intelligent-assistant.{asterisk}` and `mcp.{asterisk}`, and uses the single `use` action instead of the `read`, `create`, `update`, and `delete` actions. For the full mapping of old to new permission names, see xref:ai-feature-permissions_enable-ai-assistance-for-developers[AI feature permissions].
+
For example, the four chat permissions collapse to a single permission. Replace:
+
[source,text,subs="+quotes"]
----
p, role:default/_<team>_, lightspeed.chat.read, read, allow
p, role:default/_<team>_, lightspeed.chat.create, create, allow
p, role:default/_<team>_, lightspeed.chat.update, update, allow
p, role:default/_<team>_, lightspeed.chat.delete, delete, allow
----
+
with:
+
[source,text,subs="+quotes"]
----
p, role:default/_<team>_, intelligent-assistant.chat, use, allow
----
+
[IMPORTANT]
====
The new permission grants full access to a feature. A role cannot keep partial access, such as read-only chat or create-without-delete chat. For each role with partial access, decide whether to grant full access or no access to the feature. A `deny` on a new permission blocks the entire feature, so review inherited roles and existing denies before you migrate.
====

. Update every source that configures RBAC policies, not only the policy CSV file:
.. If you grant AI features through `permission.rbac.defaultPermissions.basicPermissions`, replace the old chat, Notebooks, and MCP entries with the new feature permissions and the `use` action. The default role applies to every authenticated user, so review previous partial grants before you consolidate them.
.. If `permission.rbac.pluginsWithPermission` contains `lightspeed`, replace that entry with `intelligent-assistant` so that the RBAC UI can discover the new permissions. Keep the other entries.
.. Update any conditional policy rules and automation scripts that reference `lightspeed.{asterisk}` identifiers.
+
For the full RBAC update procedure, including conditional policies, see xref:proc-update-rbac-policies-for-rhdh-2-1_migrate-from-rhdh-1-10-to-2-1[Update RBAC policies for {product-very-short} 2.1]. To mount updated policy files during deployment, see xref:define-authorizations-in-external-files-by-using-helm_define-policies-in-external-files-to-provision-permissions-during-cluster-deployment[Define authorizations in external files by using Helm] or xref:define-authorizations-in-external-files-by-using-the-operator_define-policies-in-external-files-to-provision-permissions-during-cluster-deployment[Define authorizations in external files by using the Operator].

. Apply the updated configuration and restart your {product-very-short} deployment. The `policyFileReload` setting reloads policy files only; changes to application configuration, such as `defaultPermissions`, require a workload rollout to take effect.

.Verification

. Verify that the `lightspeed-core` container starts without errors:
+
[source,terminal]
----
$ oc logs deployment/<deployment_name> -c lightspeed-core
----
. Open the {ia-short} chat interface and verify that the assistant responds.
. If you use Notebooks, verify that existing Notebooks are accessible from the *My Notebooks* dashboard.
. Using a fresh session for a non-administrator account that has the migrated chat permission, confirm that the chat entry points are available and that the user can send a prompt and reopen a conversation.
. Using a non-administrator account that has no effective chat grant, confirm that the chat entry points are hidden and that an authenticated request to `GET /api/intelligent-assistant/v2/conversations` returns `HTTP 403`. An unauthenticated `HTTP 401` response does not verify the policy. Use non-administrator accounts, because administrator access can hide missing grants.
. Review the {product-very-short} logs and confirm that no policy references an unrecognized `lightspeed.{asterisk}` identifier.
