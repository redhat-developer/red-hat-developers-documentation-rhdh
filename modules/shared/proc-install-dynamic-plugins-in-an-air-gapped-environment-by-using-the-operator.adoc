= Install dynamic plugins in an air-gapped environment by using the Operator

[role="_abstract"]
To install external dynamic plugins in an air-gapped environment, configure a custom NPM registry by mounting a secret into the {product-short} Operator.

[IMPORTANT]
====
When you install {product-short} by using the Operator, you must configure the secret in the `spec.application.extraFiles.secrets` field of  your {product-custom-resource-type} custom resource. Helm chart installations detect the secret automatically when you follow a specific naming convention, but Operator installations require you to reference the secret in the custom resource manually, regardless of the name you choose.
`{product-custom-resource-type}` custom resource. Unlike Helm chart installations where the secret name follows a specific naming
convention, Operator installations require manual configuration in the custom resource regardless of the secret name used.
====

.Prerequisites

* An {ocp-short} administrator has installed the {product} Operator.
* You have set up a custom NPM registry that is accessible from within your cluster and contains the required dynamic plugin packages.

.Procedure

. Create a secret containing your `.npmrc` configuration that points to your internal NPM registry:
+
[source,yaml,subs="+quotes"]
----
apiVersion: v1
kind: Secret
metadata:
  name: developer-hub-dynamic-plugins-npmrc
type: Opaque
stringData:
  .npmrc: |
    registry=https://_<your_internal_registry>_
    //_<your_internal_registry>_:_authToken=_<your_auth_token>_
----
+
where:

`name: developer-hub-dynamic-plugins-npmrc`:: The secret name can be any valid name. You will reference this name in the custom resource configuration.

. Apply the secret to your namespace:
+
[source,terminal,subs="+attributes"]
----
$ oc apply -f dynamic-plugins-npmrc.yaml -n {my-product-namespace}
----

. Add the secret to the `spec.application.extraFiles.secrets` field in your `{product-custom-resource-type}` custom resource, targeting the `install-dynamic-plugins` init container:
+
[source,yaml,subs="+attributes"]
----
apiVersion: rhdh.redhat.com/v1alpha5
kind: {product-custom-resource-type}
metadata:
  name: my-rhdh
spec:
  application:
    extraFiles:
      secrets:
        - name: developer-hub-dynamic-plugins-npmrc
          mountPath: /opt/app-root/src/.npmrc.dynamic-plugins
          containers:
            - install-dynamic-plugins
----
+
where:
+
`- name: developer-hub-dynamic-plugins-npmrc`:: The secret name must match the secret created in step 1.
`mountPath: /opt/app-root/src/.npmrc.dynamic-plugins`:: The mount path must be `/opt/app-root/src/.npmrc.dynamic-plugins` for the init container to read the configuration.
`- install-dynamic-plugins`:: The secret must be mounted to the `install-dynamic-plugins` init container.
+
The `install-dynamic-plugins` init container reads the `.npmrc` file from `/opt/app-root/src/.npmrc.dynamic-plugins/.npmrc` to resolve plugin packages from your internal registry.

. Apply the updated custom resource:
+
[source,terminal,subs="+attributes"]
----
$ oc apply -f my-rhdh.yaml -n {my-product-namespace}
----

.Verification

* Verify that the init container used your custom registry by checking the init container logs:
+
[source,terminal]
----
$ oc logs -c install-dynamic-plugins deploy/backstage-my-rhdh
----
