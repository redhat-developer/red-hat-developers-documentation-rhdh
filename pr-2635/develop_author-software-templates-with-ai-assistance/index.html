Chapter 1. The rhdh-templates skill for AI-assisted authoring

To author correct golden-path Red Hat Developer Hub (RHDH) software templates without trial and error, use the rhdh-templates skill. The skill encodes Scaffolder conventions, common gotchas, and parameter widgets so that new adopters produce convention-compliant templates.

Important

The rhdh-users-skill-pack is a community project. Red Hat does not offer official or commercial support for it. Use the skill pack at your own risk, and do not rely on it for production or business-critical workflows.

The rhdh-templates skill is a community agent skill in the rhdh-users-skill-pack repository. It works with Claude Code, Cursor, Codex, and many other coding agents. You describe your goal in plain language, and the skill guides you through authoring and validating a Red Hat Developer Hub software template.

A software template is a kind: Template entity that the Scaffolder processes. Each template combines the following artifacts:

  • template.yaml: metadata, the parameter form (spec.parameters), the actions to run (spec.steps), and outputs (spec.output).
  • skeleton/: the files copied into the generated repository, with Nunjucks placeholders in place of substituted values.
  • location.yaml: a kind: Location entity at the repository root that registers your templates for catalog import.

The skill lowers the learning curve by encoding RHDH conventions, common gotchas, and parameter widgets, and by validating templates before they reach a running instance. With AI guidance, you can convert an existing codebase into a parameterized template, author a template from scratch, add parameters, steps, and skeleton files incrementally, and validate a template locally before you confirm Scaffolder execution against a running instance.

Chapter 2. rhdh-templates skill commands

The rhdh-templates skill routes your request to a subcommand based on your goal. Use this reference to select the command that matches the task, from initial setup through local validation and remote testing.

CommandDescription

init

Check required tools, scaffold the template repository layout, and optionally probe RHDH connectivity.

templatize

Convert an existing codebase into a parameterized template. This is the most common workflow.

create

Author a template from scratch when no reference code exists.

add-parameter

Add a parameter or parameter group to an existing template.yaml.

add-step

Add a Scaffolder step to an existing template.yaml.

add-skeleton

Add or parameterize skeleton files with Nunjucks.

create-location

Generate or update the root location.yaml for catalog registration.

fix-gotchas

Auto-fix common template mistakes, such as missing {% raw %} blocks or wrong action ID casing.

validate

Run local YAML schema, gotcha, and optional Nunjucks checks without a running instance.

list-actions

List the Scaffolder actions available on a running RHDH instance.

dry-run

Test template execution through the Scaffolder v2 dry-run API.

explain-action

Show the input schema for an action or the parameter schema for a template.

examples

Browse curated reference templates from the official library and bundled examples.

Chapter 3. Install the rhdh-templates skill

To give your coding agent Red Hat Developer Hub template expertise, install the rhdh-templates skill from the community skill pack. After installation, the agent loads the skill automatically when you ask it to author or validate a template.

Important

The rhdh-users-skill-pack is a community project. Red Hat does not offer official or commercial support for it. Use the skill pack at your own risk, and do not rely on it for production or business-critical workflows.

Prerequisites

  • A supported coding agent, such as Claude Code, Cursor, or Codex.
  • Node.js and npx are available in your environment.

Procedure

  1. To install only the rhdh-templates skill, run the following command: 

    npx skills add redhat-developer/rhdh-users-skill-pack --skill rhdh-templates

    To install the full skill pack, omit the --skill flag.

  2. Optional: To target a specific agent, add the -a flag. For example: 

    npx skills add redhat-developer/rhdh-users-skill-pack -a claude-code

Verification

  1. List the available skills without installing them: 

    npx skills add redhat-developer/rhdh-users-skill-pack --list
  2. In your agent, ask it to use the skill. For example: Use the rhdh-templates skill to validate my template.yaml. The agent loads the skill and prompts you for the next step.

Chapter 4. Set up a template authoring environment

To author templates that pass validation on the first attempt, set up a repository with the layout that Red Hat Developer Hub expects. The init command checks your tools, scaffolds a starter template, and creates the root location.yaml.

Prerequisites

  • You installed the rhdh-templates skill.
  • python3 and git are available in your environment.

Procedure

  1. Ask your agent to run the init command, or run the bundled script directly from your target directory: 

    python <skill_dir>/scripts/init.py --path .

    Replace <skill_dir> with the path to the installed rhdh-templates skill.

  2. Optional: To check connectivity to a running instance, add the --rhdh-url flag: 

    python <skill_dir>/scripts/init.py --path . --rhdh-url https://rhdh.example.com
  3. Review the reported results, including any missing tools, the scaffolded paths, and the connectivity status.

Verification

  1. The templates/ directory exists and has at least one template folder.
  2. A root location.yaml exists with the target ./templates/**/template.yaml.
  3. The init script exits with code 0 (ready) or 1 (layout created, but optional tools or RHDH are unavailable).

Next steps

  • Convert a codebase into a software template
  • Create a software template from scratch
Note

For the recommended development loop, install djlint so that local validation can lint Nunjucks in skeleton files. If a running instance is unreachable, local authoring and validation still work.

Chapter 5. Convert a codebase into a software template

To reuse a working project as a golden path, convert it into a parameterized software template instead of writing one from scratch. The templatize workflow analyzes your code, proposes the values to parameterize, and builds the template only after you confirm the mapping.

The workflow is interactive at every decision point. It never edits your source until you approve the proposed parameters, so you keep control over what becomes configurable.

Prerequisites

  • You installed the rhdh-templates skill and set up a template repository.
  • You have a local copy of the source codebase to convert.

Procedure

  1. Ask your agent to templatize the codebase, and specify the source path. The skill runs a deterministic analyzer to detect the project type and candidate literals: 

    python <skill_dir>/scripts/analyze.py --path <source_dir> --json
  2. Review the candidate table that the skill presents. For each value, choose to parameterize it, keep it literal, or skip it. Parameterize identity values such as component name and owner; keep framework defaults literal.
  3. Confirm the parameter mapping. Only after your confirmation does the skill create the skeleton/ directory, copy your source files, and replace confirmed values with ${{ values.<param> }} placeholders.
  4. Let the skill generate template.yaml with your parameters and a typical fetch:template, publish, and catalog:register step sequence.

  5. Register the template by generating or updating the root location.yaml: 

    python <skill_dir>/scripts/create_location.py --path <template_repo_root>

Verification

  1. The templates/<name>/ directory has template.yaml and a skeleton/ directory, and the root location.yaml registers the template.
  2. Skeleton files reference ${{ values.* }}, not ${{ parameters.* }}.
  3. Local validation reports zero critical findings. See Validate a software template locally.

Chapter 6. Create a software template from scratch

When no reference codebase exists, create a software template from scratch with AI guidance on Red Hat Developer Hub conventions. The create workflow gathers your intent, suggests reference examples, and builds a minimal but complete template that passes validation.

Prerequisites

  • You installed the rhdh-templates skill and set up a template repository.

Procedure

  1. Tell your agent to create a template, and answer its intake questions: the golden path the template enables, the target entity type, the required form fields, the steps to include, and your source control provider.
  2. Review the reference examples that the skill suggests for your stack. You can mirror an example’s step sequence or start from the bundled minimal template.
  3. Let the skill build the template directory with template.yaml, a skeleton/ directory, and an optional README.md. In skeleton files, values use the ${{ values.* }} prefix, which the fetch:template action requires.

  4. Register the template by generating or updating the root location.yaml: 

    python <skill_dir>/scripts/create_location.py --path <repo_root>

Verification

  1. The template.yaml is a valid v1beta3 template with parameters, steps, and outputs appropriate to your use case.
  2. The skeleton/ directory has at least one templated file, and location.yaml lists the new template.
  3. Local validation and gotcha checks report zero critical findings. See Validate a software template locally.

Chapter 7. Validate a software template locally

To catch template errors before they reach a running instance, validate locally with no Red Hat Developer Hub connection required. The validate command runs YAML schema, gotcha, and optional Nunjucks checks so you can fix issues early and avoid failed catalog imports.

Prerequisites

  • You installed the rhdh-templates skill and authored a template.
  • Optional: djlint is installed for Nunjucks linting of skeleton files.

Procedure

  1. Run local validation against your template directory: 

    python <skill_dir>/scripts/validate.py --path <template_dir> --repo --json

    The --repo flag also checks the root location.yaml.

  2. To lint Nunjucks in skeleton files, add the --lint-skeleton flag: 

    python <skill_dir>/scripts/validate.py --path <template_dir> --lint-skeleton --json

  3. Auto-fix common issues, such as missing {% raw %} blocks or wrong action ID casing: 

    python <skill_dir>/scripts/fix_gotchas.py --path <template_dir>/template.yaml --apply
  4. Address any remaining findings manually, then re-run validation.

Verification

  1. Validation reports ok: true with a critical count of 0. Critical findings, such as a wrong apiVersion or invalid action casing, cause failures in the Template Editor.
  2. You reviewed all warnings and decided whether to fix them before merging.

Chapter 8. Test a template against a running RHDH instance

To confirm that the Scaffolder runs your template correctly before you publish it, test it against a running Red Hat Developer Hub (RHDH) instance. Use list-actions to verify action IDs, then use dry-run to run the template without creating real resources.

Prerequisites

  • You installed the rhdh-templates skill and validated the template locally with zero critical findings.
  • A running RHDH instance with the Scaffolder v2 API is reachable from your environment.
  • A bearer token, provided through the RHDH_TOKEN environment variable or the --token flag.

Procedure

  1. List the Scaffolder actions installed on your instance to confirm the exact action IDs used in your template: 

    python <skill_dir>/scripts/list_actions.py --rhdh-url https://rhdh.example.com --json
  2. Create a JSON file of sample parameter values that match spec.parameters. Use fake data, not real tokens or production identifiers.

  3. Run a dry-run of the template: 

    python <skill_dir>/scripts/dry_run.py \
  --rhdh-url https://rhdh.example.com \
  --path <template_dir> \
  --values /tmp/values.json \
  --json

Verification

  1. The dry-run completes with exit code 0.
  2. The log shows the expected steps, especially fetch:template, and reports the generated file count.

Troubleshooting

  • A 401 or 403 response indicates a missing or expired token. Supply a valid token.
  • An Action not found error indicates a wrong action ID. Re-run list-actions and correct the action field.
  • Empty skeleton output indicates a missing fetch:template step or wrong values wiring. Re-run local validation and fix the step.
Note

A dry-run simulates mutation steps such as publish and catalog:register. Full end-to-end verification still requires running the template in RHDH.
